# 前端表单状态容器承接后端校验结果并精准回填链路分析报告

## 一、整体架构概览

本项目是 **Gotify Server** —— 一个 Go (Gin) 后端 + React (MobX + MUI) 前端的消息推送服务系统。表单校验链路贯穿前后端，整体数据流如下：

```
用户输入 → 前端本地简易校验（按钮禁用+Tooltip）
         → Store 层发起请求（两条路径分流）
             ├─ 路径A：默认 axios 实例 → 全局拦截器 → 401特殊处理/Snackbar → Promise.reject
             └─ 路径B：axios.create() 新实例 → 局部 catch → 组件自行处理
         → 后端 DTO 层（如 ApplicationParams）参与 Bind 校验 → model 层存库
         → Gin 错误中间件格式化 → model.Error JSON 返回
```

### 2.3 错误中间件：统一格式化

**文件：[error/handler.go](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/error/handler.go#L14-L64)**

这是整个后端错误体系的核心中间件，**在所有 handler 执行完毕之后** 统一处理 `c.Errors`：

```go
func Handler() gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Next() // 先执行业务 handler

        if len(c.Errors) > 0 {
            for _, e := range c.Errors {
                switch e.Type {
                case gin.ErrorTypeBind: // 参数绑定/校验错误（validator 抛出）
                    errs, ok := e.Err.(validator.ValidationErrors)
                    if !ok {
                        writeError(c, e.Error())
                        return
                    }
                    var stringErrors []string
                    for _, err := range errs {
                        stringErrors = append(stringErrors, validationErrorToText(err))
                    }
                    writeError(c, strings.Join(stringErrors, "; "))
                default: // 其他业务错误（AbortWithError）
                    writeError(c, e.Err.Error())
                }
            }
        }
    }
}
```

### 2.4 字段名映射：后端校验字段 → 可读文本

**文件：[error/handler.go](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/error/handler.go#L43-L56)**

```go
func validationErrorToText(e validator.FieldError) string {
    // 取 Go 结构体字段名（DTO 的字段名，如 Name、Pass），首字母转小写
    runes := []rune(e.Field())
    runes[0] = unicode.ToLower(runes[0])
    fieldName := string(runes) // → "name" / "pass" / "defaultPriority" 等

    switch e.Tag() {
    case "required":
        return fmt.Sprintf("Field '%s' is required", fieldName)
    case "max":
        return fmt.Sprintf("Field '%s' must be less or equal to %s", fieldName, e.Param())
    case "min":
        return fmt.Sprintf("Field '%s' must be more or equal to %s", fieldName, e.Param())
    }
    return fmt.Sprintf("Field '%s' is not valid", fieldName)
}
```

## 三、前端请求的两条路径：全局拦截器 vs 局部 catch

### 3.1 分流的根源：默认 axios 实例 vs axios.create()

| 路径 | 发起方式 | 拦截器 | 错误处理 | 典型使用场景 |
|------|---------|--------|---------|------------|
| **路径A：全局拦截器路径** | 直接 `axios.get/post/put/delete`（使用默认实例） | ✅ 走 `initAxios` 注册的全局响应拦截器 | 拦截器处理（含 401 特殊流程）→ Snackbar → Promise.reject | 大多数 CRUD：AppStore、UserStore、ClientStore 等 |
| **路径B：局部 catch 路径** | `axios.create()` 新建实例 → `.get/.post` | ❌ **不走全局拦截器**（新实例独立） | 各方法自行 catch，或继续向外抛出 | 认证相关：login、register、tryAuthenticate、elevate |

**为什么要分流？** 认证相关请求通常需要设置特殊 headers（如 Basic Auth），或需要独立的错误处理逻辑（避免 401 触发递归 tryAuthenticate）。

### 3.2 路径A：全局拦截器（含 401 特殊处理）

**拦截器注册点：[ui/src/apiAuth.ts](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/ui/src/apiAuth.ts)**

```typescript
export const initAxios = (currentUser: CurrentUser, snack: SnackReporter) => {
    axios.interceptors.response.use(undefined, (error) => {
        // 1) 无响应 - 网络错误
        if (!error.response) {
            snack('Gotify server is not reachable, try refreshing the page.');
            return Promise.reject(error);
        }

        const status = error.response.status;

        // 2) 401 Unauthorized —— 交给 CurrentUser.tryAuthenticate() 接手
        if (status === 401) {
            currentUser.tryAuthenticate().then(() => snack('Could not complete request.'));
        }

        // 3) 400 / 403 / 500 - 业务错误，通过 snack 全局展示
        if (status === 400 || status === 403 || status === 500) {
            snack(error.response.data.error + ': ' + error.response.data.errorDescription);
        }

        return Promise.reject(error); // 无论如何都继续 reject，让 await 抛异常
    });
};
```

> **关键细节**：`tryAuthenticate()` 本身用的是 `axios.create()` 新实例（路径B），**不会再次触发这个 401 拦截器**，避免了死循环。

### 3.3 401 接手链路：CurrentUser.tryAuthenticate() 的完整处理

当全局拦截器检测到 401，会调用 `currentUser.tryAuthenticate()`。这个方法用 `axios.create()` 新实例发起 `GET /current/user` 请求，根据结果分支处理。

> **关于 tryAuthenticate 失败时是否提示（snack）的关键澄清**：
> `tryAuthenticate()` **方法自身不做任何 snack 提示**（它的 catch 分支里没有调用 `this.snack()`）。是否提示完全由调用方决定。详见下文"3.5 tryAuthenticate 各调用点的提示行为对比"。

**文件：[ui/src/CurrentUser.ts L83-L120](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/ui/src/CurrentUser.ts#L83-L120)**

```typescript
public tryAuthenticate = async (): Promise<AxiosResponse<ICurrentUser>> => {
    return axios
        .create()  // ← 新实例，不走全局拦截器，避免 401 死循环
        .get(config.get('url') + 'current/user')
        .then(
            action((passThrough) => {
                // ===== 分支1：认证成功（Cookie/session 仍有效）=====
                this.user = passThrough.data;       // 更新用户信息
                this.loggedIn = true;               // 标记已登录
                this.authenticating = false;        // 结束认证中状态
                this.connectionErrorMessage = null;  // 清除连接错误
                this.reconnectTime = 7500;           // 重置重连间隔
                return passThrough;
            })
        )
        .catch(
            action((error: AxiosError) => {
                this.authenticating = false;

                // ===== 分支2：无响应（网络断开/服务不可达）=====
                if (!error || !error.response) {
                    this.connectionError('No network connection or server unavailable.');
                    return Promise.reject(error);
                }

                // ===== 分支3：5xx（服务端错误）=====
                if (error.response.status >= 500) {
                    this.connectionError(
                        `${error.response.statusText} (code: ${error.response.status}).`
                    );
                    return Promise.reject(error);
                }

                // ===== 分支4：4xx（包括 401 未认证）=====
                this.connectionErrorMessage = null;
                if (error.response.status >= 400 && error.response.status < 500) {
                    this.logout();  // ← 主动登出，清除 loggedIn 状态
                }
                return Promise.reject(error);
            })
        );
};
```

**`connectionError()` 方法做了什么？** [ui/src/CurrentUser.ts L145-L155](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/ui/src/CurrentUser.ts#L145-L155)

```typescript
private readonly connectionError = (message: string) => {
    this.connectionErrorMessage = message;  // 设置连接错误提示
    if (this.reconnectTimeoutId !== null) {
        window.clearTimeout(this.reconnectTimeoutId);
    }
    // 指数退避重连：7.5s → 15s → 30s → 60s → 120s（上限）
    this.reconnectTimeoutId = window.setTimeout(
        () => this.tryReconnect(true),
        this.reconnectTime
    );
    this.reconnectTime = Math.min(this.reconnectTime * 2, 120000);
};
```

**各状态的改动场景汇总**：

| 状态 | 初始值 | 在何处被修改 | 修改时机 |
|------|-------|------------|---------|
| `loggedIn` | `false` | login.then、tryAuthenticate.then → `true`；logout()、tryAuthenticate.catch(4xx) → `false` | 登录成功/登出/401 |
| `authenticating` | `true` | login 开始、tryAuthenticate 开始 → `true`；login 结束、tryAuthenticate 结束（无论成败）→ `false` | 认证流程开始/结束 |
| `user` | `{name:'unknown', admin:false, id:-1, ...}` | login.then(resp.data)、tryAuthenticate.then(resp.data) | 登录/认证成功 |
| `connectionErrorMessage` | `null` | connectionError() → 错误信息；tryAuthenticate.then → `null`；tryAuthenticate.catch(4xx) → `null` | 网络异常时设置，恢复或4xx时清空 |
| `refreshKey` | `0` | [reactions.ts L70](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/ui/src/reactions.ts#L70) — 连接恢复时 `refreshKey++` | 连接错误消除后 |

**完整的 401 接手状态变化时序**：

```
拦截器检测到 401
  → currentUser.tryAuthenticate()（新 axios 实例）
    → GET /current/user 返回 401
      → tryAuthenticate.catch(4xx)
        → this.authenticating = false
        → this.connectionErrorMessage = null
        → this.logout() → this.loggedIn = false
          → reaction 触发 clearAll()：清空所有 Store 数据、关闭 WS
      → Promise.reject()
  → .then(() => snack('Could not complete request.'))
```

public login = async (username: string, password: string) => {
    runInAction(() => {
        this.loggedIn = false;       // 开始前先标记为未登录
        this.authenticating = true;  // 开始认证
    });
    const name = this.createClientName();
    axios

            data: {name},
            headers: {Authorization: 'Basic ' + btoa(username + ':' + password)},

};

## 四、前端状态容器（Store）体系

### 4.1 基础抽象：BaseStore

**文件：[ui/src/common/BaseStore.ts](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/ui/src/common/BaseStore.ts)**

```typescript
export abstract class BaseStore<T extends HasID> implements IClearable {
    @observable protected accessor items: T[] = [];

    protected abstract requestItems(): Promise<T[]>;
    protected abstract requestDelete(id: number): Promise<void>;

    @action
    public remove = async (id: number): Promise<void> => {
        await this.requestDelete(id);  // 无 catch，异常向上抛出
        await this.refresh();
    };

    @action
    public refresh = (): Promise<void> =>
        this.requestItems().then(action((items) => { this.items = items || []; }));
}
```

**设计特点**：BaseStore **完全不处理错误**，也**不保存错误状态**。异常直接向上抛出，由全局拦截器或调用方处理。

## 五、表单组件层：提交失败后弹窗留原处的确认

### 5.1 三种 Dialog 模式的行为对比

项目中的表单 Dialog 分为三种模式，**提交失败后全部都留在原处**，但机制不同：

| Dialog | submitAndClose 写法 | 失败后是否关闭 | 机制说明 |
|--------|-------------------|---------------|---------|
| AddEditUserDialog | `async/await` 后调 `fClose()` | ❌ 不关闭 | await 抛异常 → fClose() 不执行 |
| AddApplicationDialog | 同上 | ❌ 不关闭 | 同上 |
| UpdateApplicationDialog | 同上 | ❌ 不关闭 | 同上 |
| RegistrationDialog | `.then(success => { if (success) fClose() })` | ❌ 不关闭 | 失败返回 false → 条件判断不通过 |
| ElevationForm | 组件内 try-catch | ❌ 不关闭 | catch 到错误 → 设置本地 error state |

### 5.2 模式一：async/await 型（占多数）

## 六、后端校验字段名与前端输入项的对应关系

### 6.1 字段名对照总表

后端 validator 返回的字段名是 **Go DTO 结构体字段名首字母小写**，而前端表单输入项有自己的 `name` / `id` / `className`。两者**不直接对应**：

| 后端 DTO | 后端字段（json） | 前端组件 | 前端 name 属性 | 前端 id 属性 | 前端 className | 能否直接对应 |
|---------|-----------------|---------|--------------|------------|--------------|------------|
| CreateUserExternal | `name` | AddEditUserDialog 用户名 | `username` | `username` | `name` | ❌ name/username 不一致 |
| CreateUserExternal | `pass` | AddEditUserDialog 密码 | `password` | `password` | `password` | ❌ pass/password 不一致 |
| ApplicationParams | `name` | AddApplicationDialog 名称 | （无） | （无） | `name` | ❌ 无 name 属性 |
| ApplicationParams | `description` | AddApplicationDialog 描述 | （无） | （无） | `description` | ❌ 无 name 属性 |
| ApplicationParams | `defaultPriority` | AddApplicationDialog 优先级 | （无） | （无） | `priority` | ❌ 命名不一致且无 name |
| CreateUserExternal | `name` | RegistrationDialog 用户名 | `username` | `register-username` | `name` | ❌ 命名不一致 |
| CreateUserExternal | `pass` | RegistrationDialog 密码 | `password` | `register-password` | `password` | ❌ 命名不一致 |
| —（业务错误纯文本） | — | 所有场景 | — | — | — | 如 "username already exists" 无字段标识 |

### 6.2 对精准回填的影响

三层不匹配导致无法直接精准回填：
1. **后端错误格式本身不结构化**：`errorDescription` 是拼接字符串，不是 `{field: message}`
2. **字段命名不一致**：后端 `pass` vs 前端 `password`，后端 `name` vs 前端 `username`
3. **前端输入项缺少 name 属性**：很多 TextField 没有 `name`，只有 `className`
4. **业务错误无字段关联**：如 "username already exists" 是纯字符串

## 十一、总结

### 三个关键细节的确认

#### 1. 共享拦截器遇到 401 后由谁接手？CurrentUser 具体改动了哪些状态？

**接手流程**：
1. 全局拦截器检测 `status === 401` → 调用 **`currentUser.tryAuthenticate()`**
2. `tryAuthenticate()` 使用 `axios.create()` 新实例（避免递归触发拦截器）发起 `GET /current/user`
3. 分支处理：
   - **成功** → `user` 更新、`loggedIn=true`、`authenticating=false`、`connectionErrorMessage=null`、`reconnectTime=7500`
   - **4xx（包括 401 再次失败）** → `authenticating=false`、`connectionErrorMessage=null`、调用 `logout()` → `loggedIn=false` → reaction 触发 `clearAll()` 清空所有 Store 数据
   - **5xx / 无响应** → `authenticating=false`、`connectionErrorMessage=xxx`、设置指数退避重连定时器（7.5s→15s→30s→60s→120s）
4. `.then()` 无论成功失败都 snack `"Could not complete request."`
5. 最后 `return Promise.reject(error)` 让原始调用方的 await 抛异常

**CurrentUser 全部 observable 状态**：`loggedIn`、`authenticating`、`user`、`connectionErrorMessage`、`refreshKey`。

#### 2. Application 链路里真正参与绑定校验的是哪层结构？

**是 `api.ApplicationParams`（DTO 层），不是 `model.Application`（Model 层）**：
- `ApplicationParams` 定义在 [api/application.go L34-L57](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/api/application.go#L34-L57)，只有 4 个字段：Name（`binding:"required"`）、Description、DefaultPriority、SortKey
- CreateApplication 和 UpdateApplication 中 `ctx.Bind(&applicationParams)` 绑定的都是这个 DTO
- 校验通过后再手动把 DTO 字段**拷贝**到 `model.Application`（Create）或**合并**到已有 Model（Update）
- `model.Application` 虽然也有 binding tag，但在 Create/Update 流程中不参与 Bind，只是作为 GORM 数据库模型使用

#### 3. 提交失败后弹窗是否留在原处？

**✅ 全部留在原处**，三种模式机制不同但结果一致：
- async/await 模式（多数）：`await fOnSubmit()` 抛异常 → `fClose()` 被跳过
- Promise.then + success 模式（Register）：`success=false` → `if (success) fClose()` 不执行
- try-catch 模式（ElevationForm）：catch 处理错误，弹窗当然不关
