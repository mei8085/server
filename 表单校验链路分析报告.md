# 前端表单状态容器承接后端校验结果并精准回填链路分析报告

## 一、整体架构概览

本项目是 **Gotify Server** —— 一个 Go (Gin) 后端 + React (MobX + MUI) 前端的消息推送服务系统。表单校验链路贯穿前后端，整体数据流如下：

```
用户输入 → 前端本地简单校验 → Store层发起axios请求 → 后端Gin参数绑定校验
                                                                 ↓
前端错误回填 ← axios拦截器统一处理 ← model.Error结构化JSON ← 错误中间件格式化
```

### 2.3 错误中间件：统一格式化

**文件：[error/handler.go](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/error/handler.go#L14-L64)**

这是整个后端错误体系的核心：

```go
func Handler() gin.HandlerFunc {
    return func(c *gin.Context) {
        c.Next() // 执行后续处理

        if len(c.Errors) > 0 {
            for _, e := range c.Errors {
                switch e.Type {
                case gin.ErrorTypeBind: // 参数绑定/校验错误
                    errs, ok := e.Err.(validator.ValidationErrors)
                    if !ok {
                        writeError(c, e.Error())
                        return
                    }
                    var stringErrors []string
                    for _, err := range errs {
                        // 将每个校验错误转为可读文本
                        stringErrors = append(stringErrors, validationErrorToText(err))
                    }
                    writeError(c, strings.Join(stringErrors, "; "))
                default: // 其他业务错误
                    writeError(c, e.Err.Error())
                }
            }
        }
    }
}

// 校验错误 → 人类可读文本
func validationErrorToText(e validator.FieldError) string {
    runes := []rune(e.Field())
    runes[0] = unicode.ToLower(runes[0])
    fieldName := string(runes) // 首字母小写，对应 json 字段名
    switch e.Tag() {
    case "required":
        return fmt.Sprintf("Field '%s' is required", fieldName)
    case "max":
        return fmt.Sprintf("Field '%s' must be less or equal to %s", fieldName, e.Param())
    case "min":
        return fmt.Sprintf("Field '%s' must be more or equal to %s", fieldName, e.Param())
    }
    return fmt.Sprintf("Field '%s' is not valid", fieldName)
}
```

```typescript
export abstract class BaseStore<T extends HasID> implements IClearable {
    @observable protected accessor items: T[] = [];

    @action
    public remove = async (id: number): Promise<void> => {
        await this.requestDelete(id);  // 无 catch，异常向外抛出
        await this.refresh();
    };

    @action
    public refresh = (): Promise<void> =>
        this.requestItems().then(action((items) => { this.items = items || []; }));
}
```

**设计特点**：BaseStore 中**完全不处理错误**，axios Promise 异常直接向上抛出，由 axios 全局拦截器统一处理。

## 四、前端错误处理的核心：Axios 拦截器

**文件：[ui/src/apiAuth.ts](file:///d:/fz/0601-1/solo-dogfeeding/code/37-server/ui/src/apiAuth.ts)**

这是前端承接后端校验结果的**统一入口**，也是整个链路中最关键的一环：

```typescript
export const initAxios = (currentUser: CurrentUser, snack: SnackReporter) => {
    axios.interceptors.response.use(undefined, (error) => {
        // 1) 无响应 - 网络错误
        if (!error.response) {
            snack('Gotify server is not reachable, try refreshing the page.');
            return Promise.reject(error);
        }

        const status = error.response.status;

        // 2) 401 Unauthorized - 会话失效，触发重新认证
        if (status === 401) {
            currentUser.tryAuthenticate().then(() => snack('Could not complete request.'));
        }

        // 3) 400 / 403 / 500 - 业务错误，通过 snack 全局展示
        if (status === 400 || status === 403 || status === 500) {
            snack(error.response.data.error + ': ' + error.response.data.errorDescription);
        }

        return Promise.reject(error); // 继续向上抛出，让调用方有机会处理
    });
};
```

## 七、当前架构的局限性分析

### 7.1 后端侧的结构缺陷

| 问题 | 具体表现 | 影响 |
|------|---------|------|
| 错误非结构化 | `errorDescription` 是 `"; "` 拼接的字符串 | 前端无法解析出「哪个字段错了」 |
| 字段名不统一 | 后端返回 Go 结构体字段名（首字母小写化），与前端表单 `name` 属性不直接对应 | 需要额外映射 |
| 丢失多重校验 | 如果同一字段同时违反多个规则，只按 tag 顺序返回一条 | 信息不完整 |

### 7.2 前端侧的处理缺失

| 问题 | 具体表现 | 影响 |
|------|---------|------|
| 统一拦截器粒度太粗 | 所有 400/403/500 全部走 snack | 无法实现字段级差异化处理 |
| Store 层无错误状态 | BaseStore 及子类不保留错误信息 | 组件无法读取错误进行回填 |
| 表单组件缺少 error 属性绑定 | 多数 TextField 未设置 `error` + `helperText` | 即使有错误也无法高亮 |
| Dialog 提交无 try-catch | 后端返回错误后 fClose 是否执行不确定 | 用户体验不一致 |

## 八、实现精准字段级回填的改进建议

### 8.1 后端改造：结构化错误响应

```go
type Error struct {
    Error            string              `json:"error"`
    ErrorCode        int                 `json:"errorCode"`
    ErrorDescription string              `json:"errorDescription"`
    FieldErrors      map[string]string   `json:"fieldErrors,omitempty"` // 新增
}

func writeError(ctx *gin.Context, errString string, fieldErrors map[string]string) {
    ...
    ctx.JSON(status, &model.Error{
        Error:            http.StatusText(status),
        ErrorCode:        status,
        ErrorDescription: errString,
        FieldErrors:      fieldErrors,
    })
}
```

### 8.2 前端改造：Store 层增加错误容器

在 BaseStore 或各业务 Store 中增加字段级错误状态：

```typescript
export abstract class BaseStore<T extends HasID> implements IClearable {
    @observable accessor items: T[] = [];
    @observable accessor fieldErrors: Record<string, string> = {}; // 新增

    @action
    protected setFieldErrors = (errors: Record<string, string>) => {
        this.fieldErrors = errors;
    };

    @action
    protected clearFieldErrors = () => {
        this.fieldErrors = {};
    };
}
```

## 十、总结

### 现行链路
1. **前端本地校验**通过 Tooltip + Button disabled 实现（简单必填）
2. **Store 发起 axios 请求**，异常不做本地 catch
3. **后端参数绑定校验**（validator）+ **业务校验**（数据库/权限）
4. **Gin 错误中间件**将所有错误格式化为 `model.Error` 的字符串描述
5. **axios 响应拦截器**统一捕获 → 顶部 Snackbar 展示
6. **ElevationForm 是例外**：单独 try-catch + 本地 error state + TextField error 属性

### 精准回填的缺失环节
- ❌ 后端错误不是 `{field: message}` 结构 → 前端无法"精准"识别字段
- ❌ Store 层不保留错误状态 → 组件无法从 Store 读取错误
- ❌ 表单组件 TextField 未绑定 error/helperText → 有错误也显示不出来
- ❌ Dialog 提交缺少 try-catch → 错误发生后的行为不可控

项目当前实现的是**全局提示（Snackbar）模式**，能够完成"反馈"但未做到"精准回填"。要实现真正的字段级精准回填，需要按照第八章的建议，从**后端错误结构结构化 → Store增加错误状态 → 组件绑定 error 属性**三层同步改造。
